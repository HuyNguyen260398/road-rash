## C1 — Stop publishing the author's email as `authorName` (Medium / privacy)

**Problem.** `getDisplayName` ranks `email` above `cognito:username`/`sub`. The result is stored
as `trip.authorName` and rendered on the **public** `/trip/[id]` share page. A Google account
whose token omits a `name` claim publishes the user's email to anonymous visitors.

**Files.** `services/shared/auth.ts:29-38` (write path → `services/trips/handler.ts:193` →
public render `components/TripDetail.tsx:182`).

**Fix.** Remove `email` from the fallback chain.

```diff
--- a/services/shared/auth.ts
+++ b/services/shared/auth.ts
@@ export function getDisplayName(
   const c = claims(event) ?? {};
-  for (const key of ["name", "email", "cognito:username", "sub"]) {
+  // Never fall back to `email` — authorName is rendered on the public share
+  // page (components/TripDetail.tsx), so an email would leak publicly (C1).
+  for (const key of ["name", "cognito:username", "sub"]) {
     const value = c[key];
     if (typeof value === "string" && value.length > 0) return value;
   }
   return "Unknown";
 }
```

**Verify.** Unit test on `getDisplayName` with claims `{ email: "x@y.com" }` (no `name`) must
return something that is **not** the email (i.e. `cognito:username` or `sub`, else `"Unknown"`).
Note: existing trips already in DynamoDB may carry an email in `authorName` — a one-off
backfill/scrub may be warranted (similar in spirit to `scripts/reconcile-favorites.ts`).

## C2 — URL-encode `mid` in the embed builder (Medium-Low / robustness + defense-in-depth)

**Problem.** `toMyMapsEmbedUrl` interpolates a URL-decoded, charset-unchecked `mid` straight
into the embed URL (`...embed?mid=${mid}`). A `mid` containing `#`, `&`, or whitespace corrupts
the query (`#`→fragment, `&`→extra param) and breaks the map. XSS is currently blocked by React
attribute-escaping + the host-locked target + CSP `frame-src`, so this is robustness and
defense-in-depth, not an active injection — but the unencoded interpolation is the kind of habit
that becomes a vulnerability if copied to a non-escaped surface.

**Files.** `lib/validation.ts:33-34` (validator allows any non-empty `mid`), `:42-50` (builder).

**Fix.** Encode in the builder; optionally tighten the validator's `mid` charset.

```diff
--- a/lib/validation.ts
+++ b/lib/validation.ts
@@ export function validateMyMapsUrl(url: string): boolean {
   const mid = parsed.searchParams.get("mid");
-  return mid !== null && mid.length > 0;
+  // Real My Maps ids are URL-safe (alphanumerics, `-`, `_`). Constraining the
+  // charset keeps a corrupted/hostile `mid` out of the embed src (C2).
+  return mid !== null && /^[A-Za-z0-9_-]+$/.test(mid);
 }
@@ export function toMyMapsEmbedUrl(url: string): string {
   const mid = new URL(url).searchParams.get("mid");
   // Normalize host + path so the rendered iframe is always the canonical embed
   // endpoint regardless of which share/view variant the user pasted.
-  return `https://www.google.com/maps/d/embed?mid=${mid}`;
+  return `https://www.google.com/maps/d/embed?mid=${encodeURIComponent(mid!)}`;
 }
```

**Verify.** `validateMyMapsUrl(".../viewer?mid=a b")` → `false`; `toMyMapsEmbedUrl` over a valid
`mid` round-trips unchanged; a `mid` with a reserved char never appears raw in the output.
**Watch:** if any legitimate existing `mid` contains characters outside `[A-Za-z0-9_-]`, the
charset tightening would newly reject it — if unsure, ship only the `encodeURIComponent` half and
keep the `length > 0` check.

## C3 — Namespace-validate `thumbnailKey` on write (Low / authz consistency)

**Problem.** `validateTripInput` only trims + length-caps `thumbnailKey`. The upload side scopes
keys to `thumbnails/<sub>/…`, but the trip write accepts any string, so a bypassed client can set
a trip's `thumbnailKey` to another user's key or a prefix-less junk value. Low impact (thumbnails
are public; the public GET route already requires the prefix) but it's an authz gap vs. the
upload-side scoping.

**Files.** `services/trips/validate.ts:50` (read) and `:115` (output).

**Fix.** Reject keys outside the thumbnails prefix.

```diff
--- a/services/trips/validate.ts
+++ b/services/trips/validate.ts
@@ (after the length-cap block, before the myMapsUrl check)
+  // A thumbnailKey must reference the server-issued thumbnails namespace — a
+  // bypassed client must not point a trip at an arbitrary bucket key (C3).
+  if (thumbnailKey && !thumbnailKey.startsWith("thumbnails/")) {
+    return { ok: false, message: "thumbnailKey is invalid" };
+  }
```

**Verify.** `validateTripInput({ …valid, thumbnailKey: "etc/passwd" })` → `{ ok: false }`;
`thumbnailKey: "thumbnails/<sub>/x.jpg"` → accepted; empty/absent → accepted (it's optional).
**Stronger option:** thread the caller's `sub` into the validator and require
`thumbnails/<sub>/` — closes cross-user reference entirely, at the cost of changing the validator
signature.

## C4 — Case-insensitive server search OR document the boundary (Low)

**Problem.** Server free-text search uses DynamoDB `contains` (case-sensitive) and truncates to
200 results *before* the client refines (`lib/search.ts`). A lowercase query can drop uppercase
matches once the dataset exceeds the first page/200 cap.

**Files.** `services/trips/handler.ts:90-97, 168`.

**Recommendation.** Acceptable for the launch dataset (ASSUMPTION-001). Before any data-growth
event, either lower-case a normalized search attribute at write time and match against it, or move
to the documented Option B (OpenSearch). For now: add a code comment marking the boundary and a
note in `docs/` so it isn't forgotten. No code change required yet.

## C5 — Unpaginated Scan silently truncates at scale (Low)

**Problem.** `listTrips` issues a single `ScanCommand` (first 1 MB page only); the `group` sort and
`slice(0, 200)` operate on that partial page, so grouping/ordering silently degrades past ~1 MB of
items.

**Files.** `services/trips/handler.ts:150-168`.

**Recommendation.** Documented as ASSUMPTION-001 and fine for MVP scale. If/when the table grows,
paginate the Scan (or the GSI Query) before sorting, or adopt Option B. No code change required
yet — track as a known scaling boundary.
